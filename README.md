# Daltar Kenya — Rebuild

Monorepo: `/frontend` (Next.js + TypeScript + Tailwind) and `/backend` (FastAPI).

These files were hand-written rather than generated by `create-next-app`/`pip install`
(no network access on the build side), so the first step below installs everything
for real and confirms it boots.

## Frontend

```bash
cd frontend
cp .env.example .env.local
npm install
npm run dev
```

Visit http://localhost:3000 — you should see "Daltar Kenya — scaffold OK".

## Backend

```bash
cd backend
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env
uvicorn app.main:app --reload
```

Visit http://localhost:8000/health — you should see `{"status":"ok"}`.

## Phase 9 — Neon database + first migration

1. Create a free Neon project at https://neon.tech if you haven't already.
2. Copy the **pooled** connection string from the Neon dashboard (Connection Details →
   check "Pooled connection"). It looks like:
   ```
   postgresql://user:password@ep-xxxx-pooler.region.aws.neon.tech/dbname?sslmode=require
   ```
3. Paste it into `backend/.env` as `DATABASE_URL`, replacing the placeholder.
   **Important:** add `+psycopg` right after `postgresql` in the URL — we installed
   the `psycopg` (v3) driver in `requirements.txt`, and SQLAlchemy defaults a bare
   `postgresql://` URL to the psycopg2 driver, which isn't installed here. So:
   ```
   DATABASE_URL=postgresql+psycopg://user:password@ep-xxxx-pooler.region.aws.neon.tech/dbname?sslmode=require
   ```
   not `postgresql://...` — that will fail with a driver-not-found error.
4. Run the migration:
   ```bash
   cd backend
   source venv/bin/activate
   alembic upgrade head
   ```
5. Start the server and check the new route:
   ```bash
   uvicorn app.main:app --reload
   ```
   Visit http://localhost:8000/db-health — you should see
   `{"status":"ok","database":"connected"}`.
6. Optional sanity check directly against Neon (via its SQL editor or `psql`):
   ```sql
   select * from users;
   ```
   Should return an empty table with the right columns (id, email, hashed_password,
   full_name, company_name, role, created_at) — no rows yet, that's expected until
   Phase 10 adds registration.

## Phase 10 — testing the auth endpoints

No Postman/curl needed — FastAPI serves interactive docs automatically. With the
server running (`python -m uvicorn app.main:app --reload` if `uvicorn` alone
isn't on your PATH), visit:

```
http://localhost:8000/docs
```

1. Expand **POST /api/auth/register**, click "Try it out", fill in a test email/
   password/full_name, execute. You should get back a `201` with an
   `access_token` and a `user` object.
2. Copy the `access_token` value. Click the "Authorize" button (top right of the
   docs page), paste the token in as `Bearer <token>` (or just the raw token,
   depending on how the docs page prompts you), and authorize.
3. Expand **GET /api/auth/me**, try it out, execute — it should return the same
   user you just registered.
4. Expand **POST /api/auth/login** with the same email/password — should return
   a fresh token.
5. Try registering the same email twice — second attempt should return `409
   Email already registered`.
6. Try `/me` with no token authorized, or an obviously wrong one — should
   return `401`.

## Phase 10 — done when

- [ ] `/me` returns the right user when authorized, 401 when not

## Phase 11 — Redis (verify later, alongside Neon)

Redis needs a real instance too — easiest free option for local dev is
[Upstash](https://upstash.com) (serverless Redis, gives you a `redis://` or
`rediss://` connection string) or running Redis in Docker locally
(`docker run -p 6379:6379 redis`). Either way, put the connection string in
`backend/.env` as `REDIS_URL`.

When you do the full verification pass:
- [ ] `/redis-health` returns `{"status":"ok","redis":"connected"}`
- [ ] Hitting `/api/auth/login` with the wrong password 6 times in a row (within
      5 minutes) returns `429 Too many attempts` on the 6th try
- [ ] Registering 11 accounts from the same machine within an hour gets rate
      limited on the 11th (loose limit — this one's mostly to stop scripted
      spam signups, not real users)
- [ ] Log in, copy the token, call `/logout` with it, then try `/me` with that
      same token again — should now return 401 "Token has been revoked"
      instead of succeeding
- [ ] A *different*, still-valid token (e.g. log in again to get a fresh one)
      still works on `/me` after the above — confirms logout only revokes the
      one token, not all of a user's sessions

## Phase 15 — Deployment (Vercel + Railway + Neon)

Local dev and production run the exact same code — only environment
variables differ. New files for this phase: `backend/Procfile` (tells
Railway how to start the app) and `backend/.python-version` (pins Python
3.14, matching everything already fixed against that version locally).

### Order of operations (this order matters — see the circular CORS note below)
1. Push to GitHub (both `frontend/` and `backend/`)
2. Prepare a production Neon database (a Neon branch, or a second project)
3. Create a Railway project, root directory `backend`, add env vars
   (`DATABASE_URL`, `REDIS_URL`, a **new** `JWT_SECRET`, `PAYSTACK_SECRET_KEY`;
   leave `CORS_ORIGINS`/`FRONTEND_URL` as localhost for now)
4. Add Railway's Redis addon, link its URL into the backend service
5. Deploy, then run `railway run python -m alembic upgrade head` against
   production — deploying code does NOT run migrations for you
6. Create a Vercel project, root directory `frontend`, set
   `NEXT_PUBLIC_API_URL` to the Railway URL from step 5, deploy
7. **Circular CORS fix-up:** go back to Railway, update `CORS_ORIGINS` and
   `FRONTEND_URL` to the real Vercel URL from step 6 — this couldn't be done
   until the Vercel URL existed, which is why it's a separate step, not part
   of step 3
8. Update Paystack's webhook URL to the real Railway address — no more ngrok
   needed once this is live
9. Full login → purchase test, on the real URLs

### Done when
- [ ] Visiting the Vercel URL loads the site correctly, all pages, all images
- [ ] Register/login works against the production database
- [ ] A test purchase completes, Paystack webhook fires, order flips to `paid`
      without any local tunnel running
- [ ] `/staff` and `/admin` role gates still work correctly in production
- [ ] Browser console shows no CORS errors on any page
